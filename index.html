Pharmacy Claims Lakehouse

Independent project · Databricks

Business challenge

Reporting built on legacy SQL Server and Alteryx pipelines is hard to re-run and hard to audit, so a wrong number can reach leadership, and a decision, before anyone notices.

Objective

Show what the same reporting looks like when it is reproducible, auditable and trustworthy by design.

Thinking

Treat data quality as a business control: reconcile every row, decide what to reject and what to flag, and stop the pipeline before bad numbers are published.

Implementation

A governed Databricks lakehouse. A million synthetic pharmacy claims, with the mess real files have, flow through bronze, silver and gold layers to a dashboard. 34 data quality checks; one serverless job runs everything in about 9 minutes.

Outcome

998,498 rows received reconcile to 887,876 final claims, every reject has a reason, and one-contract-per-claim logic avoids a $0.58M double count in rebate estimates (synthetic data).

WHAT THIS DEMONSTRATES

Lakehouse architectureHealthcare data modellingData quality & reconciliationCommercial analytics
More technical detail

Three of the 54 design decisions

  • Cancel before de-duplicating. Done the other way round, a resent copy of a cancelled claim comes back as paid
  • Reject only what can't be used; flag the rest. A claim paid outside a member's eligibility still cost money, so it stays in spend, flagged for recovery
  • Two severities. A pipeline bug stops the job; expected source mess is tolerated up to a limit and reported, so nobody learns to ignore the alerts

Under the hood

  • Safe to re-run: incremental loading and idempotent writes give identical results on every run, with an audit table
  • Domain logic in the model: product codes standardised (39% arrived non-standard), and contract precedence avoids a 3.4% double count in rebate estimates
  • 54 design decisions documented, each with its reason and the alternative considered

24 monthly deliveries plus one late file, as CSV. The mess is put in on purpose: mixed product-code formats, reversals, rebills, duplicates and resends, unknown members, fills outside eligibility.

Decision: files land by arrival month, not fill month, so late data is a real problem to solve, not a theory.

▼Auto Loader

Auto Loader picks up only new files. Every column lands as text, exactly as received, with the source file, load time and run ID attached. Each file is reconciled to an answer key.

Decision: bronze is append-only, so every later layer can be rebuilt from it at any time.

Drug Unit Converter

Independent project · Python

Business challenge

Drug claim lines often arrive with a quantity but no reliable unit. Is "10" ten vials, ten mL or ten billing units? Read it wrong and every cost figure built on it is wrong too.

Objective

Work out the unit automatically, and be honest when it can't be worked out.

Thinking

Score each possible reading on structure and on price, and explain the answer with a confidence level instead of making a silent guess.

Implementation

A Python rules engine on public US reference data (FDA, CMS), with single-line and CSV batch modes, tested with pytest and deployed as a live Streamlit app.

Outcome

About 99.7% accurate on simulated single-package claims when an allowed amount is present (about 70% without). Claims it can't resolve are flagged as undecided, not guessed.

WHAT THIS DEMONSTRATES

Rules-based problem solvingPharmaceutical domain knowledgeReference-data integrationExplainable results & testing
More technical detail
  • Scores both readings on structure (whole vials, package counts, whole HCPCS billing units, waste) and on price against ASP and NADAC reference prices
  • Handles billing modifiers: combines JW/JZ waste lines and RT/LT laterality lines, and links KP/KQ lines before converting
  • Reference data: FDA NDC Directory, CMS ASP crosswalk and NADAC, refreshed by script
